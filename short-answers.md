**1. Hiding password lengths.**
Before encryption, every password is padded to a fixed-size block: a 2-byte length prefix, the password bytes, then zero padding up to 256 bytes (64 characters × 4 bytes per UTF-8 character, which covers the 64-character maximum even with multi-byte characters). The padded block is encrypted with AES-GCM, so every ciphertext has the same length regardless of the real password length. The true length is recovered after decryption from the prefix, which is inside the authenticated ciphertext.

**2. Preventing swap attacks.**
Each record is encrypted with AES-GCM using the record's KVS key, HMAC(k_domain, domain), as the *additional authenticated data* (AAD). The GCM tag covers both the ciphertext and the AAD. In `get`, we recompute the tag for the requested domain and decrypt with that value as the AAD. If an adversary moves the record for `www.google.com` under the key for `www.evil.com`, the AAD used for decryption (HMAC of evil.com) differs from the one used at encryption (HMAC of google.com), so GCM authentication fails and we throw. Forging a valid record for a different AAD would require breaking AES-GCM's authenticity, and the adversary cannot compute domain tags without the secret HMAC key. This defense works independently of the SHA-256 checksum.

**3. Is trusted storage necessary for rollback defense?**
Yes. A rolled-back record or database is a previously valid, correctly authenticated state, so every MAC and AES-GCM tag in it still verifies, and the keychain cannot tell old from new using only data that the adversary can overwrite. Detecting rollback requires some state the adversary cannot revert (a trusted hash, a monotonic counter, or a trusted server). If the adversary could modify that storage too, they could roll it back along with the data.

**4. Lookup with a randomized MAC.**
With a randomized MAC, the tag for a domain differs on every run, so we can't compute the tag and do a dictionary lookup. Instead, we would store each entry under its randomized tag and, to look up domain x, iterate over all entries and run MAC verification `verify(k, x, tag)` on each stored tag until one succeeds. This makes lookup (and set/update/remove, which first look up the domain) O(n) instead of O(1), with n MAC verifications per operation.

**5. Leaking only ⌊log₂ k⌋ of the record count.**
Add dummy records so the stored count is always the next power of two above the real count (or equivalent: pad to 2^⌈log₂ k⌉). Dummy entries have random keys and random ciphertexts of the same size as real ones (encrypting padded dummy blocks), so they look identical to real records. We keep a count of real records (inside the encrypted/authenticated portion, e.g. in the password check record) so lookups still work, and when real records exceed the current capacity we double the number of dummies. The adversary then only sees the power-of-two size, so any k1, k2 with the same ⌈log₂⌉ are indistinguishable. Cost: up to 2× storage.

**6. Multi-user support for a shared site.**
Alice and Bob keep their own keychains with their own master keys. For the shared entry (e.g. nytimes) they agree on a separate *shared key* pair (HMAC key + AES-GCM key) used only for that record, generated randomly by one of them and given to the other, for example by encrypting it under the other's public key (public-key encryption / key exchange) and storing it in each person's own keychain. The shared record is stored in a shared location, with its domain tag and encryption computed with the shared keys and the same AAD binding. Either user can read and update it, while their other entries remain protected by their own master-derived keys that the other does not have. Compromise of the shared key exposes only that site. If a user leaves, rotate the shared key and re-encrypt the record.
